# Helios Signal v0.1 — Retrieval / Ranking / Clustering / Learning / Evaluation Audit

**Scope only:** retrieval, ranking, clustering, learning, evaluation. **Date:** 14 Nov 2026. **Auditor:** specialist researcher (subagent). **User:** Vedant Swami, Helios Signal v0.1 — Python modular monolith, PostgreSQL + pgvector, hybrid retrieval, S(s,c)= wrR+wiI+wnN+weE+waA+wtT−wdD, 6 memory layers, Plan→Retrieve→Connect→Evaluate→Recommend→Record.\
**Method:** every star / license / release date below was checked live via browser.search on 14 Nov 2026. Anything not confirmed live is marked **UNVERIFIED**. Star counts drift daily — treat as ±\~2% snapshots, not exact. Prices are list prices on the dates cited; re-check before spending.\
**Known context carried in:** IWM 11 Nov 2026 — hybrid RAG + LazyGraphRAG-shaped summarisation; no benchmark exists for attribution quality / provenance fidelity / cross-domain recall / continual updating — build your own pre-registered gold set. Cost dominated by model inference (2–3 orders over infra); extraction tier is a 50–70× lever. MS GraphRAG maintenance mode since Aug 2026, full indexing 100–1,000× vector RAG cost.

## 0. Headline verdicts (read this first)

1. **KEEP pgvector + Postgres tsvector + RRF (k=60) + a frozen rules baseline.** That is the correct v0.1 spine. Do not add a second vector DB.
2. **REPLACE Cohere Rerank as the default with bge-reranker-v2-m3 (self-hosted, CPU-capable) and keep Cohere Rerank 5 only as a paid A/B arm.** Cohere is now per-token ($0.05/1M Pro, $0.02/1M Fast, launched 21 Oct 2026) — cheap at Helios scale, but it is a vendor dependency with no offline path and no score calibration you control.
3. **REPLACE the embedding default if it is bge-large-en-v1.5 with bge-m3 (or Qwen3-Embedding-0.6B).** bge-large is English-only, 512-token, legacy (no new BGE embedder since Jul 2024). bge-m3 is MIT, 8K context, 100+ langs, dense+sparse+multi-vector in one pass.
4. **DO NOT USE Jina embeddings/rerankers in a commercial product without a paid licence.** v3/v5 are CC-BY-NC-4.0; v4 is Qwen research (non-commercial). This is the single most likely licence trap in the stack.
5. **DO NOT adopt MS GraphRAG as a dependency. BUILD LazyGraphRAG-shaped summarisation in-house** (cheap noun-phrase / GLiNER graph at index time, LLM summarisation only of the retrieved subgraph at query time). LightRAG is the only live GraphRAG alternative worth reading — as a pattern, not a dependency.
6. **DO NOT adopt Ragas for new work.** Dormant since 24 Feb 2026 (v0.4.3, 13 Jan 2026), founders moved to Vibrant Labs, CVE-2026-6587 unpatched. Use DeepEval (OSS, Apache-2.0) for pytest-style evals + plain Python + SQLite/Parquet for the gold set. Do not pay for LangSmith/Confident AI yet.
7. **The highest-leverage change in the whole layer is not a model — it is the gold set + point-in-time discipline.** Without a pre-registered, timestamp-frozen gold set (see §9), every ranking-weight change (wr…wd) and every reranker swap is unfalsifiable. Build that before tuning S(s,c).
8. **Clustering: do not ship BERTopic as a batch job and call it "signal discovery".** Use HDBSCAN (via scikit-learn 1.8+, not the stale standalone package) on UMAP-reduced embeddings for offline discovery, plus a cheap incremental rule (near-duplicate / same-entity + time-window) for live signals. Top2Vec is dead; Leiden is GPL-3.0 — keep it behind a process boundary or avoid it.

## 3. Hybrid retrieval — RRF

| Component                    | ChatGPT choice           | Open-source pointer(s)                                                                                                                                                                                                                                                                  | Verdict  | $0 workaround                                          | Change that matters                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Reciprocal Rank Fusion (RRF) | KEEP (implied by hybrid) | No repo — algorithm, Cormack, Clarke & Büttcher, SIGIR 2009. Formula: `RRF(d) = Σ 1/(k + rank_i(d))`, k=60 canonical. 7 lines of Python. Also implemented in `ranx` (UNVERIFIED stars/date — not checked live) and natively in Elasticsearch/OpenSearch/Weaviate/Qdrant/Azure AI Search | **KEEP** | Already $0 — write it yourself, \~15 lines, with tests | Fuse **3** lists, not 2: (1) pgvector HNSW, (2) Postgres FTS/BM25, (3) recency/entity-boost list. Log the per-list rank of every surfaced signal so you can later learn weights. Do NOT fuse raw scores (cosine ∈ [−1,1] vs BM25 unbounded) without normalisation — that is the #1 homegrown hybrid bug. Tune k on the gold set; 60 is a starting point, not a law |

**Pipeline order for Helios:** retrieve top-50 per leg → RRF fuse → cross-encoder rerank top-50→top-10 → apply S(s,c) business weights → present top-N with provenance. Reranking before the business weights, not after, or the reranker will silently override recency/novelty.

**Gold-set recipe (pre-registered, \~1 day of work, $0):**

1. **Freeze the universe first.** Write down the bounded universe (e.g. 20–50 people, 10–20 companies, 30-day window) in `gold/v1/SCOPE.md` and git-tag it. A gold set without a frozen universe is not reproducible.
2. **Collect 50–100 real questions** (the actual questions Helios will answer: "who is driving the X narrative?", "what changed for company Y this week?"). Each gets: `query_id`, `query_text`, `asked_at` (timestamp), `asker`, `intent`.
3. **Label relevance by hand, before any model runs.** For each query, list the gold documents/signals with graded relevance (0/1/2) + a one-line *why* + the provenance (URL + accessed_at). Two labellers, or one labeller + a second-pass review; record inter-labeller agreement. **Never label from the model's own top-10** — that bakes the model's biases into the truth.
4. **Pre-register the scoring rule in writing before the first run:** metrics (nDCG\@10 primary; Recall\@10, MRR\@10 secondary), the frozen baseline (rules S(s,c) v1), the promotion threshold (+3 nDCG\@10, held-out only), and the rule that a failed run stays on the record. Hash the qrels file (SHA-256) and commit it. Any edit after the first run creates `v2` — v1 is never edited.
5. **Split by time, not at random** (see §10). Train/validation/test = past / recent-past / most-recent. A random split leaks the future.
6. **Score in CI.** `pytest tests/test_gold.py` runs the frozen baseline + the current pipeline on the gold set and fails the build on regression. The accuracy log is the public output of this file.
7. **Size honestly:** 50 queries × \~10 judged docs is enough to detect a 5-point nDCG move; it is not enough to detect a 1-point move, and that is fine — Helios v0.1 should only promote large, real wins.

## 13. What ChatGPT's architecture gets right, what to fix, and the build order

**Right:** Postgres + pgvector as one store; hybrid (dense + lexical) rather than dense-only; a frozen rules baseline before learning; a learning loop with feedback rather than "the LLM will learn"; LazyGraphRAG-shaped thinking over full GraphRAG.\
**Fix:** (1) name the embedding/reranker defaults with licences attached (Jina and MonoT5 are traps; bge-large is legacy); (2) replace Ragas with DeepEval before writing any eval code; (3) replace standalone HDBSCAN/Top2Vec with sklearn HDBSCAN + BERTopic-offline; (4) quarantine Leiden (GPL-3.0); (5) do not import MS GraphRAG or LightRAG as dependencies in v0.1.\
**Build order (v0.1):** ① bitemporal schema + `as_of` on every retrieval; ② pgvector HNSW (`halfvec`, bge-m3 via FastEmbed) + Postgres FTS + RRF(k=60) + frozen S(s,c) v1; ③ gold set v1 (50–100 queries, pre-registered, hashed) + CI gate (nDCG\@10); ④ bge-reranker-v2-m3 on RRF top-50, A/B vs no-reranker; ⑤ BERTopic weekly offline + incremental live detector (NN + time-window); ⑥ LazyGraphRAG-shaped query-time summarisation (NP graph only at index); ⑦ log actions → labelled pairs → LightGBM LambdaRank offline, promote only on +3 nDCG\@10 held-out. **Do not start step ④ or ⑦ before step ③ exists.**
